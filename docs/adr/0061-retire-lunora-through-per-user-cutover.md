# Retire Lunora through per-user cutover

Status: accepted

Lunora is retired by migrating each user independently from a frozen Lunora snapshot into the classic Durable Object, then switching that user to classic before writes resume. This supersedes ADR 0058's planned Lunora cutover: classic remains the only user-facing outline backend, while Lunora shards stay retained and read-only through the observation period.

Every Better Auth user is inspected from D1's authoritative user list. Preference-off users remain on classic; a preference-off user with Lunora data requires manual review because either backend might contain the newer edits. A Lunora snapshot is eligible for automatic migration only when one consistent, versioned export contains every Lunora table, has at least one node, passes row schemas and ownership checks, and has valid unique keys, references, and complete acyclic sibling chains.

Manual review can use a one-user, admin-session-gated read-only comparison of current classic and Lunora snapshots. It reports ids, graph validation, saved preference, changed-field names, and side-collection difference counts, without returning outline or side-collection content. It bypasses the migration state machine and creates no audit records, backups, or write fences. The reads are not simultaneous or frozen, so the comparison cannot establish which backend is authoritative or authorize repair. Schema, version, and ownership failures reject the comparison; migration eligibility rules remain unchanged.

Daily-index mappings are retained claims, not node-graph references. Deletion or undo can leave a claim whose node is absent; daily get-or-create can materialize that node under its claimed id. Both snapshot validators accept this state while retaining schema, ownership, unique-key, and node-graph checks. Cutover preserves every Lunora claim in the classic target without merging old classic claims; the immutable classic backup preserves its own claims for rollback.

Migration metadata and attempts live in D1. Immutable pre-migration classic and Lunora snapshots live in R2 under a unique migration id and must survive write-read validation before classic changes. Failed or manual-review users prevent the 30-day observation period from starting; deleting migration backups, Lunora bindings, or shard data is a separate infrastructure change that requires explicit approval.

Both backends freeze writes before export so an override or stale tab cannot race the restore. The restored classic snapshot takes nodes and the three shared side-collections from Lunora, preserves classic-only changelog and account preferences, stamps a resume barrier so older clients receive the replacement snapshot, and disables the Lunora preference before classic resumes. A preference-off user with Lunora data is classified `backend-conflict` and never migrated automatically.

Operator HTTP operations stay one-user and idempotent; a dry-run-first Bun CLI owns batching. If post-restore verification fails, the operator restores and verifies the immutable classic backup and leaves both backends frozen whenever the resulting state is uncertain. Migration tooling ships before runtime removal; after every eligible user is safely on classic, a separate application release removes the toggle and normal Lunora browser and MCP paths while retaining the read-only shard and export binding for the observation period.

The per-user operation is a resumable state machine with one durable migration id across D1, R2, Lunora, and classic. It freezes and exports classic first, freezes and exports Lunora second, verifies both immutable R2 objects, atomically restores classic with the migration id, verifies the complete restored snapshot, marks Lunora retired, and unfreezes classic. A retry resumes that operation; a completed user is a no-op. Failures before classic changes release both freezes, a verified rollback may also release them, and an uncertain state remains frozen for operator recovery.

Every dry-run, migration, retry, and restore atomically claims its user's D1 record with a unique invocation id before reading either backend. This invocation id is distinct from the durable migration id: two executors must not share operation ownership merely because they resume the same migration. A competing request returns 409 without backend calls. Ownership covers rollback, recovery, and attempt recording and is released only when the invocation finishes. The claim has no expiry or automatic takeover. If an executor terminates before release, an operator must confirm it and its outstanding RPCs have stopped before clearing the exact recorded claim. A client timeout or old claim timestamp is not proof that execution stopped.

An operator restore after Lunora is already retired restores the pre-migration classic content but keeps the Lunora preference disabled. A retired shard cannot be reopened, and restoring its old enabled preference would route MCP and reconnecting clients back to a permanently frozen backend.

The migration adds no temporary synchronization between backends. Connected Lunora clients learn the shard is retired and reload onto classic only after classic verification; the permanent server-side freeze remains the safety boundary. Report classifications add `backend-conflict` and `classic-invalid` where the proposed vocabulary could not describe a safe automatic action. Reports and logs contain stable user ids, state, counts, hashes, timestamps, snapshot keys, and failure reasons, but never node text.

## Manual resolution preserves the user's chosen classic copy

If a user has returned to classic and chooses to keep it, resolve the conflict through a separate preserve-classic operation, not automatic migration or timestamp-based merging. Keep all classic nodes and side-collections unchanged. Archive both complete frozen snapshots before retiring experimental writes. The experimental archive must also retain raw stored rows and ownership: the current exporter normalizes nodes and stamps ownership during projection, so its projection alone cannot establish archival fidelity. Source graph anomalies remain evidence, not permission to repair either source.

After retirement, an optional, separate additive import creates **Recovered experimental content** at the root. It contains two sections: nodes present only in experimental, and shared nodes whose text, task state, completion, kind, or mirror reference differs. These are alternatives, not automatically newer edits or proven lost nodes. Timestamp-only, ordering-only, and view/provenance differences stay in the archive. Experimental daily mappings, tag colors, and saved queries also stay in the archive; none replaces classic values.

Every copy has a fresh id. Copy only the ancestor context needed for selected nodes, not unrelated descendants; mark context as context and remove its task/completion state. Rebuild sibling chains after pruning. Missing parents, parent cycles, and invalid sibling order get deterministic placement in the copy and explicit adaptation records. Never borrow a missing experimental parent from classic. Reserve ids from both snapshots, retained daily claims, and missing references before allocating copy ids.

Recovery copies are ordinary editable nodes, so they participate in search, tags, and task results. All have `mirrorOf: null`; mirror locations become marked archive-reference placeholders rather than live mirrors. Remap recognized node links to selected non-mirror copies, including forward links across sections. Other tokens remain unchanged and may navigate classic or remain unresolved; external URLs are not rewritten. Editable copies are adapted content, not the faithful archive.

The preserve-classic operation must retain durable invocation ownership, matching write fences, immutable verified archives, and a receipt binding its policy and snapshots. Verify classic without replacing its nodes or KV. Once writes reopen, a retry finishes audit only; it must not restore an old snapshot over newer edits. Permanent retirement must override browser preferences and MCP force-on. A plan invalidated by reopened writes requires a new immutable revision.

The recovery import must persist its id allocation and manifest, reject existing-id collisions rather than upsert, and atomically attach its root to the current classic root tail together with an import receipt. Retries must not overwrite edited copies or recreate a deleted recovery folder. Snapshot restore and point-in-time recovery paths need fault tests for fence bypasses before production execution.

Implementation: [`planClassicRecovery`](../../worker/lunora-recovery.ts) builds detached copies; the [coordinator](../../worker/lunora-retirement-service.ts) owns verified raw archives, durable manifests, and separate `preserve-classic` / `recover-classic` operations. The [classic DO](../../worker/outline-do.ts) owns atomic preservation and import receipts, current-root attachment, collision rejection, and permanent routing metadata. Recovery requires the exact reviewed manifest hash. Neither manual operation supports batching. The content-free API reports counts and hashes, never manifest content.

Generic snapshot replacement is unavailable after permanent retirement, and PITR is unavailable once a retirement receipt exists. The explicit automatic-policy rollback remains separate; it cannot overwrite a preserve-classic account or re-enable experimental routing. Before a preservation receipt exists, a safely failed operation releases both fences without restoring data. A new explicitly requested preserve operation may create a fresh immutable revision only when both backends are unfenced and no preservation or replacement has committed. Old objects and attempt records remain retained. Once preservation commits, an interrupted retry verifies retained artifacts and finishes retirement/routing/audit without reading or replacing current classic content.

## Enabled accounts can retain Classic alternatives in the working outline

An explicitly approved `migrate-with-recovery` operation keeps the complete validated experimental outline authoritative and appends **Recovered Classic content**. It uses the existing detached-copy planner in the opposite direction: Classic-only nodes and substantive Classic alternatives get fresh ids, while metadata-only differences and Classic side-collections remain in the immutable archive. No timestamp decides authority. A small node count does not authorize dropping either snapshot or assuming disjoint ids represent identical content.

Both backends freeze and all archives pass write-read verification before the coordinator persists the versioned recovery manifest. The experimental nodes and side-collections retain their source ids and values; only the detached recovery root attaches to the experimental root tail. The existing Classic replacement transaction installs the complete target and its migration receipt together. Post-replacement verification compares that entire target before experimental writes are retired and Classic reopens.

The separate `experimental-primary-recovery-v1` policy is selected only before any prior cutover or immutable backup. Ordinary `migrate` behavior and preserve-Classic operations remain unchanged. Recovery manifests bind the user, migration id, both source hashes, and copy allocation. Retries reuse the persisted manifest and reject hash or binding changes. Completed retries never replace current edits or recreate deleted copies. This operation is one-user only, requires production-write approval, and cannot be added to an already completed migration.
